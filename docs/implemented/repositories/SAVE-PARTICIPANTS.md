# Optional infrastructure save participants

`IRepositorySaveParticipant<TContext>` lets infrastructure stage its own tracked rows before a
shared unit-of-work save. An application-owned change journal or outbox adapter can use the actual
selected context and its transaction without adding infrastructure arguments to generated ports.
RepoGen does not define messages, publication decisions, dispatch, or an outbox schema.

This is an explicit infrastructure registration in `RonSijm.RepoGen.EntityFrameworkCore`, not a
new service-side query API or designer/CLI flag. Simple/direct-context repositories remain unchanged.
Nothing is registered, executed, or generated by default. EF-free application contracts do not gain
context handles, callback arguments, or a dependency on this interface.

## Registration and use

```csharp
// Infrastructure composition, not an application-facing contract.
var work = new RepositoryUnitOfWork<MyContext>(leaseProvider);
work.RegisterSaveParticipant(adapter, adapter);

// Register this same work as IDbContextLeaseProvider<MyContext> for participating repositories.
await using (work)
await using (var transaction = await work.BeginTransactionAsync(cancellationToken: cancellationToken))
{
    await writes.StageRenameAsync(request, cancellationToken);
    await work.SaveChangesAsync(cancellationToken);
    await transaction.CommitAsync(cancellationToken);
}
```

An adapter implements `ValueTask SavingAsync(MyContext context, CancellationToken cancellationToken)`.
It may inspect changed entries and stage application-defined tracked data using the supplied context.
It must not call `SaveChanges`, begin/complete transactions, re-enter its work, or perform external
side effects. It is trusted infrastructure code, not a sandbox around the supplied EF context.

Registration is de-duplicated by **reference identity**, with the first registration winning;
different objects remain distinct even if their `Equals` results match. Participants run sequentially
in registration order, so later participants see earlier staged changes. Configure them before the
first save. Re-registering an existing identity is a no-op; a new identity after that point is rejected.
Constructors retain their existing signatures. Ordinary DI can register adapters and configure the
work in its existing scoped factory; no extra required service or registration package is added.

`KeyedRepositoryUnitOfWork<TContext,TKey>` supports the same registration, before or after its first
keyed acquisition. It forwards participants to the work bound to that key; it still rejects database
switches. Bind the first key before beginning the transaction. Participant registration alone never
acquires a context or resolves a database key.

## Save and transaction semantics

With participants installed, saving requires an **explicit transaction owned by the unit of work**.
A missing transaction is rejected before callbacks or EF persistence; the caller can begin one and
try again. External/ambient transactions retain their existing rejection rules.

For each explicit save:

1. Validate caller-supplied dependency tags and acquire the work's existing context.
2. Run participants on that context with the save's cancellation token.
3. Collect changed-type/dependent tags, including rows staged by participants.
4. Save all tracked changes together through EF.
5. Accumulate tags until the explicit transaction commits; only then notify commit observers.

The save count includes participant rows and other repositories' changes; it is not scoped to the
calling repository. A generated tracked command configured with `.Save()` uses this hook when its
lease provider is the shared work, and retains its configured result/status behavior. `.Stage()`
does not invoke participants until a later shared save. No-op saves still invoke callbacks; adapters
must deliberately select applicable pending changes and avoid creating duplicate records.

`CommitAsync` does **not** implicitly prepare or save. Immediate set-based, native returning, and
atomic writes also do not automatically invoke tracked-save participants. To combine such writes
with infrastructure rows, use the same explicit transaction and deliberately stage/save those rows.
`RecordChangesAsync` records dependency tags; it is not an audit/publication callback. Operations
that bypass the shared work's save also bypass this hook. Existing EF save interceptors remain usable.

## Failure, cancellation, and retry

Participant callbacks and native EF saves propagate their original failures. Once preparation has
started, a preparation/save/tag-validation/cancellation failure makes that work **rollback-only**:
further acquisition, writes, saves and commit are refused. Roll back or dispose it, then use a new
work and context. This prevents replaying partially prepared tracked data or committing earlier
transactional writes after preparation failed. Unfinished owned transactions roll back on disposal.

Cancellation and invalid additional tags detected before preparation do not invoke callbacks or
poison the work. Cancellation is checked between callbacks and before EF persistence even if an
adapter ignores its token. Re-entering acquire/save/begin/record/commit/rollback/dispose/registration
from preparation fails immediately rather than waiting on the work's own gate.

Rollback never notifies commit observers. It does not reconstruct an EF tracker or an arbitrary
entity graph. Borrowed contexts remain caller-owned; after a failed or rolled-back work, discard
that context or explicitly reconcile its tracking state before unrelated reuse.

The existing `RepositoryTransactionRunner` can replay an explicitly replayable callback with fresh
owned work/context state. Register/configure participants inside each attempt. Their logic must be
replayable and must not publish external effects. Failed attempts' database rows are rolled back;
only the winning commit notifies observers. Unknown commit outcomes still require application
idempotency/verification, and stale client versions are not automatically retried into success.

An observer/cleanup failure **after commit** retains the existing `RepositoryCommitException`
semantics: the database committed, including participant rows. It is not a preparation failure and
must not cause blind write replay. Cache invalidation remains commit-coordinated, not a guarantee
of distributed durability. Saving an application-owned outbox row can be atomic with other tracked
rows, but this hook alone is not a complete transactional outbox or delivery guarantee.

## Example and verification

The [Ledger example](../../../samples/ConfigurationExamples/Ledger/Program.cs) explicitly registers a
small save-receipt adapter in two scopes. A generated patch and its receipt roll back together in
one scope and commit together in the next. The receipt entity is excluded by the existing designer
allowlist, so no new repository, generated contract, or API-baseline update is needed. Its earlier
unconfigured scopes and all simpler examples keep their existing behavior.

Relational tests exercise shared tags and commit/rollback, registration/ownership/key isolation,
native and preparation failures, cancellation, fail-fast re-entry, generated Stage/Save commands,
cached queries depending on participant-owned tables, and fresh-context execution-strategy replay.

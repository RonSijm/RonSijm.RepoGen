# RonSijm.RepoGen

RonSijm.RepoGen generates design-time configured, strongly typed Entity Framework Core repository
APIs, including queries, projections, writes, pagination, caching hooks, and unit-of-work helpers.
Repositories decide which rows are eligible, generated selector extensions decide which shape to
materialize, and EF Core keeps the whole operation lazy until a terminal method is called.

```csharp
[GenerateSelectors]
public sealed class Patient
{
    public Guid Id { get; set; }
    public string Name { get; set; } = null!;
    public string Email { get; set; } = null!;
}

[ProjectionFrom<Patient>]
public sealed record PatientSummaryDto(Guid Id, string Name);
```

A manually written repository returns a generated selector without executing the query:

```csharp
public PatientSelector ByEmail(string email) =>
    new(context, context.Patients.Where(patient => patient.Email == email));
```

The caller chooses the terminal projection:

```csharp
var summary = await repository
    .ByEmail(email)
    .AsSummaryDtoAsync(cancellationToken);
```

The generated operation is equivalent to applying `Select` before
`SingleOrDefaultAsync`, so EF Core selects only the DTO columns. Collection selectors provide
`AsEntitiesAsync`, plural projection methods, `CountAsync`, and `ExistsAsync`. The underlying
`IQueryable<TEntity>` and selector constructors are internal.

## Mapping

Constructor parameters and writable DTO properties map to readable entity properties or fields
with the same name and an implicit, null-safe conversion. A DTO can supply a custom translatable
expression for computed mappings:

```csharp
[ProjectionFrom<Patient>(MethodName = "AsCard")]
public sealed record PatientCard(string Label)
{
    public static Expression<Func<Patient, PatientCard>> Projection =>
        patient => new(patient.FirstName + " " + patient.LastName);
}
```

Invalid mappings are reported at compile time as `RG001` through `RG005` diagnostics.

## Repository generation

The separate design-time executable builds an EF Core project, instantiates its `DbContext`, and
generates lookup repositories from primary keys and indexes in the final EF model:

```powershell
dotnet run --project src/RonSijm.RepoGen.Tool -- generate `
  --project path/to/My.Database.csproj
```

Primary keys and unique indexes return single selectors; non-unique indexes return collection
selectors. When the target assembly already contains selector types generated by
`RonSijm.RepoGen.Generator`, repositories reuse them. Otherwise the generated file includes the
minimal entity selector types and terminal operations needed by the repositories.

Generated lookup methods use the fluent `By...` form, such as `ById` and `ByEmail`.
Repositories also expose `GetAll`, `GetAllUnordered`, single and range forms of `Add`, `Update`, and
`Remove`, and `SaveChanges`/`SaveChangesAsync`. Single selectors inherit from the shared
`BaseEntitySelector<TEntity>`. `UpdateAsync`, `DeleteAsync`, and `RemoveAsync` persist immediately;
`StageUpdateAsync` and `MarkForDeletionAsync` only change the shared context's change tracker.
Both selector shapes provide `AsNoTracking()` and `AsTracking()` while keeping the query lazy.
Collection selectors always provide `Where`, `OrderBy`/`ThenBy`, `Skip`, `Take`, ad-hoc
`ProjectToListAsync`, `FirstOrDefaultAsync`, `ToDictionaryAsync`, grouped aggregate projections,
`ToPagedListAsync`, and
`MinAsync`/`MaxAsync`/`SumAsync`/`AverageAsync`. Both selector shapes
provide typed `Include` and ad-hoc predicates; single selectors provide `ProjectToAsync`.
Selectors support saved fluent mutations such as
`ById(id).Delete().SaveChangesAsync(cancellationToken)` and
`ById(id).Update(change).SaveChangesAsync(cancellationToken)`. Use the explicitly named staging
methods when several tracked operations should be committed by one later repository
`SaveChangesAsync` call. Repository saves are unit-of-work operations: they save every tracked
change in the shared `DbContext`, including changes made through another repository using that
context; they are not scoped to the repository entity type.
The repository has a concurrency-aware `SaveChangesAsync` overload that accepts a retry count and
conflict resolver. `ExecuteInTransactionAsync` wraps operations across repositories in an ambient
transaction; the selected EF provider must support `TransactionScope` enlistment.
Generated repository implementations receive the scoped `DbContext` directly by default. This is
the simplest and least surprising lifetime model for the usual single-database application. Enable
`UseDbContextResolver()` only when the context must be selected at runtime, for example by tenant or
database. Resolver mode generates `IDbContextResolver<TContext>` and
`ScopedDbContextResolver<TContext>` and resolves the context at each repository entry point. A
custom resolver must return the same context throughout one unit of work so staged changes,
transactions, and `SaveChanges` operate on the same change tracker.
Use `--generate-selectors` when the generated repository file should always own those selector
types; this makes regeneration deterministic even when the previous output is part of the assembly
being inspected.

Every generated repository also has an `ICacheable...Repository` interface and cache decorator.
Caching is explicit at the terminal operation, so existing selectors and projections remain lazy:

```csharp
var burger = await cacheableRepository.GetOrCreateCachedAsync(
    $"by-id:{id}",
    (repository, token) => repository
        .ById(id)
        .AsNoTracking()
        .AsBurgerDtoAsync(token),
    cancellationToken);
```

The decorator consumes the generated `IRepositoryCacheProvider` abstraction. Implement that one
provider over `IMemoryCache`, `IDistributedCache`, or another cache and register it once; the
generated decorators supply repository-specific cache keys and invalidation tags. The provider is
responsible for serialization, expiration, stampede control, and tag invalidation semantics.
Successful repository `SaveChanges` calls invalidate the repository tag. Fluent
`Update(...).SaveChangesAsync()` and `Delete().SaveChangesAsync()` operations carry the same
invalidation callback through selector chaining. Staged writes are not invalidated until they are
persisted. In multi-tenant systems, include the tenant/database discriminator in caller-supplied
cache keys when a cache provider is shared between tenants.

Designer queries configured with `.Cache(...)` use the decorator automatically. Cache options can
set absolute and sliding lifetimes, and `DependsOn<TEntity>()` adds cross-repository invalidation.

## Repository designer

For repository surfaces that go beyond EF keys and indexes, create a small design-time project,
reference `RonSijm.RepoGen.Design`, and configure the model in code:

```csharp
public sealed class PatientRepositoryDesigner : RepositoryDesigner
{
    protected override void OnModelCreating(RepositoryModelBuilder modelBuilder)
    {
        modelBuilder.Configure(options => options
            .UseDbContextResolver() // opt in for tenant/database selection
            .UseDefaultTracking(RepositoryTrackingBehavior.NoTracking)
            .GenerateTransactions(false));

        modelBuilder.Entity<Patient>(entity =>
        {
            entity.HasAccessor(patient => patient.LastName);
            entity.HasAccessor(patient => patient.Email).IsUnique();
            entity.Exclude(patient => patient.InternalSequence);
            entity.HasFilter<string>(
                "ByLastNamePrefix",
                (patient, prefix) => patient.LastName.StartsWith(prefix));
            entity.HasFilter<DateOnly, DateOnly>(
                "BornBetween",
                (patient, from, through) =>
                    patient.DateOfBirth >= from && patient.DateOfBirth <= through);
            entity.HasDefaultSort(patient => patient.LastName);
            entity.HasDefaultSort(patient => patient.FirstName);
            entity.HasSortableFields(
                patient => patient.LastName,
                patient => patient.DateOfBirth);
            entity.Include(patient => patient.Practice);
            entity.ProjectTo<PatientSummaryDto>(patient =>
                new PatientSummaryDto(patient.Id, patient.DisplayName));
        });
    }
}
```

`Configure` controls cross-cutting generated infrastructure. Direct `DbContext` injection is the
default; resolver mode is opt-in. Cache decorators, batch operations, concurrency retry,
transactions, and synchronous methods are generated by default for compatibility and can each be
disabled with `GenerateCacheDecorator(false)`, `GenerateBatchOperations(false)`,
`GenerateConcurrencyRetry(false)`, `GenerateTransactions(false)`, and
`GenerateSynchronousMethods(false)`. Generic set-based selector writes are disabled by default;
enable them with `GenerateSetBasedOperations()` only for projects referencing EF Core Relational or
a relational provider. `UseDefaultTracking(...)` supplies the starting tracking behavior for
generated selectors and for named queries that do not specify one themselves.
Per-query and fluent tracking configuration still wins.
Disabling cache generation also makes configured `.Cache(...)` policies inactive, so generated
query extensions do not depend on cache infrastructure that was intentionally omitted.

`HasAccessor` defaults to a collection selector and can be followed by `IsUnique()` or
`HasMethodName(...)`. `Exclude` takes precedence over accessors inferred from the EF model and over
explicit accessors. `HasFilter` accepts one to four typed arguments; its expression can use
comparisons, ranges, string methods, multiple properties, navigations, or any other operation the
configured EF provider can translate. A filter can be marked `IsUnique()` to return a single
selector. Repeated `HasDefaultSort` calls create `OrderBy`/`ThenBy` defaults, and `Include`
configures eager-loaded navigations. `HasSortableFields` generates a case-insensitive
`OrderBy(string fieldName, bool descending)` overload that only recognizes the configured
properties; it does not construct expressions through reflection or accept arbitrary member names.
`ProjectTo` expressions are emitted as typed selector extensions and remain inside the EF
`IQueryable`, so only the projected columns are selected.

For application services, prefer a complete named operation over rebuilding selector chains at
each call site:

```csharp
var activePatients = entity.HasFragment(
    "ActivePatients",
    patient => patient.IsActive);

entity.HasQuery("GetPatientPage")
    .Use(activePatients)
    .Where<string>((patient, prefix) => patient.LastName.StartsWith(prefix))
    .AllowSorting(patient => patient.LastName, patient => patient.DateOfBirth)
    .Include(patient => patient.Practice)
    .AsNoTracking()
    .AsSplitQuery()
    .TagWith("patient-page")
    .ProjectTo(patient => new PatientSummaryDto(patient.Id, patient.DisplayName))
    .Cache(cache => cache.For(TimeSpan.FromMinutes(5)).DependsOn<Practice>())
    .Paged();
```

This emits one closed `GetPatientPageAsync(...)` method. Other terminal shapes are `List`,
`Single`, `SingleOrDefault`, `FirstOrDefault`, `CursorPaged`, grouped `GroupBy`, `Exists`, `Count`,
and `Stream`. Runtime inputs appear as explicit generated parameters; dynamic sort fields remain
limited to that query's configured whitelist.

Named set-based commands keep update/delete predicates and assignments in the designer as well:

```csharp
entity.HasCommand("DeactivatePatients")
    .Where<Guid>((patient, practiceId) => patient.PracticeId == practiceId)
    .Update(update => update.SetProperty(patient => patient.IsActive, false));

entity.HasCommand("DeletePatient")
    .Where<Guid>((patient, id) => patient.Id == id)
    .Delete();
```

These commands use EF Core's relational `ExecuteUpdateAsync` and `ExecuteDeleteAsync`, return the
affected-row count, and invalidate configured repository cache tags. Projects that configure them
must reference `Microsoft.EntityFrameworkCore.Relational` or a relational provider package.
Named commands are the preferred application-service API because their predicates and assignments
remain fixed at design time. When infrastructure code genuinely needs a composable set-based
operation, opt in globally and use the collection selector directly:

```csharp
modelBuilder.Configure(options => options.GenerateSetBasedOperations());

var deleted = await repository
    .ByPracticeId(practiceId)
    .ExecuteDeleteAsync(cancellationToken);

var updated = await repository
    .ByPracticeId(practiceId)
    .ExecuteUpdateAsync(
        setters => setters.SetProperty(patient => patient.IsActive, false),
        cancellationToken);
```

These methods execute immediately as one SQL statement, bypass EF's change tracker, and cannot be
staged for a later `SaveChangesAsync`. They still participate in a surrounding database transaction
and invalidate the repository cache tag after affecting rows.

Navigation properties referenced by a configured projection are detected from the EF model and
included automatically for that projection only:

```csharp
entity.ProjectTo<PatientWithVisitsDto>(patient =>
    new PatientWithVisitsDto(patient.Id, patient.Visits.ToList()));
```

When navigation usage is hidden behind an expression that cannot be inferred, configure the
projection include explicitly:

```csharp
entity.ProjectTo<PatientSummaryDto>(patient =>
        new PatientSummaryDto(patient.Id, patient.DisplayName))
    .Include(patient => patient.Practice);
```

Use `entity.Include(...)` instead when the navigation should be eager-loaded by every generated
query for the entity.

Ad-hoc partial projections do not need designer configuration or a declared DTO when consumed in
the same method:

```csharp
var page = await repository.GetAll()
    .Where(patient => patient.IsActive)
    .OrderBy(patient => patient.LastName)
    .Skip(offset)
    .Take(pageSize)
    .ProjectToListAsync(patient => new { patient.Id, patient.DisplayName }, cancellationToken);
```

Grouped reporting projections keep aggregation in SQL:

```csharp
var totals = await repository.GetAll()
    .GroupBy(patient => patient.PracticeId)
    .ProjectToListAsync(group => new
    {
        PracticeId = group.Key,
        Count = group.Count(),
        TotalScore = group.Sum(patient => patient.Score),
        MaximumScore = group.Max(patient => patient.Score)
    }, cancellationToken);
```

Paging is one-based and returns the page metadata and items together. The projection overload
avoids materializing complete entities:

```csharp
PagedResult<PatientSummaryDto> page = await repository.GetAll()
    .OrderBy(sortBy, descending)
    .ToPagedListAsync(
        patient => new PatientSummaryDto(patient.Id, patient.DisplayName),
        page: 2,
        pageSize: 25,
        cancellationToken);
```

`ToPagedListAsync` performs a count query followed by the paged item query through one API call.
Callers should apply a deterministic sort before paging; a configured default sort already does so.

Pass the designer project and the consumer-side projection output to the executable:

```powershell
RonSijm.RepoGen.Tool.exe generate `
  --project path/to/My.Database.csproj `
  --designer-project path/to/My.RepositoryDesigner.csproj `
  --designer PatientRepositoryDesigner `
  --output path/to/My.Database/Generated/Repositories.g.cs `
  --projection-output path/to/My.Application/Generated/Projections.g.cs `
  --generate-selectors
```

Nested entity types remain outside this version.
